# KUKULCAN.SharedKernel.i18n — Internationalization Service

**KUKULCAN.SharedKernel.i18n** platform internationalization microservice. Provides:

- **Translation**: lookup by unique code (`MODULE + NNNN`) and language, with automatic fallback to English.
- **Locale configuration**: date and time formats, decimal and thousands separators.
- **Currency formats**: symbol, position, spacing, decimals, and negative pattern.

### Applied DDD Principles

| Concept | Implementation |
|---|---|
| **Aggregate Root** | `Language` and `Translation` — entry point to their respective aggregates |
| **Value Object** | `LanguageCode`, `TranslationCode` — immutable, value-based equality |
| **Domain Service** | `TranslationDomainService` (fallback), `LanguageDomainService` (default transfer) |
| **Repository** | nterface in Domain, implementation in Infrastructure |
| **Domain Events** | `LanguageCreatedEvent`, `TranslationCreatedEvent`, `TranslationTextUpdatedEvent` |
| **Factory Method** | `Language.Create(...)`, `Translation.Create(...)`, etc. |
| **Ubiquitous Language** | `TranslationCode`, `LanguageCode`, `CurrencySymbolPosition`, `FirstDayOfWeek` |

## Docker

The project provides a root-level `Dockerfile` for containerizing the ASP.NET Core 10 API. Docker is used for local execution, CI runtime validation, and production image publication.

### Cross-platform local deployment scripts

The repository includes three local deployment helpers under `Documentation/Scripts/Docker/`:

| Platform | Script |
|---|---|
| Linux | `KUKULCAN.SharedKernel.i18n-docker-linux.sh` |
| macOS | `KUKULCAN.SharedKernel.i18n-docker-macos.sh` |
| Windows PowerShell | `KUKULCAN.SharedKernel.i18n-docker-windows.ps1` |

These scripts are intended for a local environment where PostgreSQL is already running in the Docker container `mypostgres` and the target database is `Atlas`.

They perform the complete local deployment flow:

1. Check Docker and required tools.
2. Check the repository `Dockerfile`.
3. Obtain the PostgreSQL password without storing it in the repository.
4. Obtain or generate a JWT signing secret with the required minimum length.
5. Verify that `mypostgres` is running.
6. Create or reuse the `kukulcan-local` Docker network.
7. Attach `mypostgres` to that network when necessary.
8. Verify PostgreSQL readiness and that the `Atlas` database exists.
9. Build `kukulcan-i18n:local`.
10. Replace the previous `kukulcan-i18n` container and start a new one.
11. Verify `/health/live` and `/health/ready`.

The scripts display the current progress as a percentage and stop immediately when a command returns an error. The failing command's output is left visible; when container startup or health checks fail, the container logs are also displayed.

On Linux and macOS, make the shell script executable once:

```bash
chmod +x Documentation/Scripts/Docker/KUKULCAN.SharedKernel.i18n-docker-linux.sh
chmod +x Documentation/Scripts/Docker/KUKULCAN.SharedKernel.i18n-docker-macos.sh
```

The scripts use these local defaults:

```text
PostgreSQL container: mypostgres
PostgreSQL host:      mypostgres
PostgreSQL port:      5432
Database:             Atlas
Database user:        postgres
Database provider:    PostgresSql
Docker network:       kukulcan-local
API container:        kukulcan-i18n
API host port:        8080
Docker image:         kukulcan-i18n:local
JWT issuer:           ATLAS
JWT audience:         ATLAS.i18n
Redis:                disabled by default (MemoryCache)
```

The PostgreSQL password can be provided through `KUKULCAN_I18N_DB_PASSWORD`; otherwise the scripts prompt for it. The JWT secret can be provided through `KUKULCAN_I18N_JWT_SECRET`; otherwise the scripts prompt for it and can generate a temporary local secret.

Optional script-level overrides include:


The scripts pass the runtime configuration to the API using the .NET configuration hierarchy, notably `Kukulcan__Database__Provider`, `Kukulcan__Database__ConnectionString`, `Kukulcan__Database__Migration__AutoMigrateOnStartup`, `Kukulcan__Database__Migration__SeedDataOnStartup`, `Jwt__SecretKey`, `Jwt__Issuer`, `Jwt__Audience`, and `ConnectionStrings__Redis`.

These helper scripts are local deployment tools. They do not replace the CI Docker smoke test or the Docker Hub publication workflow.

### Build the Docker image

Run the following command from the repository root:

```bash
docker build --tag kukulcan-i18n:local .
```

The image uses a multi-stage build. The build stage uses the .NET 10 SDK image and publishes the API in `Release` configuration. The runtime stage uses the ASP.NET 10 runtime image.

### Run the API container

Start the image and publish container port `8080` to host port `8080`:

```bash
docker run --detach \
  --name kukulcan-i18n \
  --publish 8080:8080 \
  --env ASPNETCORE_HTTP_PORTS=8080 \
  kukulcan-i18n:local
```

Verify that the container is running:

```bash
docker ps
docker logs kukulcan-i18n
```

Verify the liveness endpoint:

```bash
curl --fail http://127.0.0.1:8080/health/live
```

Stop and remove the container:

```bash
docker rm --force kukulcan-i18n
```

### Run with application configuration

Configuration can be supplied through environment variables. For example:

```bash
docker run --detach \
  --name kukulcan-i18n \
  --publish 8080:8080 \
  --env ASPNETCORE_HTTP_PORTS=8080 \
  --env KUKULCAN__Database__ConnectionString='Host=<database-host>;Port=5432;Database=<database>;Username=<username>;Password=<password>' \
  --env Jwt__SecretKey='<application-secret>' \
  kukulcan-i18n:local
```

Replace the placeholder values with environment-specific configuration.

Do not commit real database passwords, JWT secrets, Docker Hub tokens, or other credentials to the repository.

## KUKULCAN Code Conventions

### Translation Code Format

A translation code follows the format **`{MÓDULO}{NNNN}`**:

| Parte | Descripción                                               | Ejemplo |
|---|-----------------------------------------------------------|---|
| `MÓDULO` | 2–5 uppercase letters identifying the owning ATLAS API | `CRM`, `PIM`, `WMS`, `AUTH`, `CORE` |
| `NNNN` | 4-digit sequential number with leading zeros              | `0001` … `9999` |

Valid examples: `CRM0001`, `PIM0042`, `AUTH0010`, `CORE0001`, `ATLAS0001`

### Fallback Rule

If a translation is requested in language X and it does not exist, the service automatically returns the **English (EN)** version. 
The field `isFallback: true`  in the response indicates that the fallback is being used.

### Default Language

English (`EN`) is the platform’s default language. **Every translation must have an EN version**. 
The delete endpoint protects EN records from accidental deletion.

## Main Endpoints

### Translations

```
GET    /api/v1/translations/{code}/{lang}           → Get text (with EN fallback)
GET    /api/v1/translations/module/{module}/{lang}  → Full module dictionary
GET    /api/v1/translations                         → Paginated list (admin)
POST   /api/v1/translations                         → Create translation
PUT    /api/v1/translations/{code}/{lang}           → Update text
PATCH  /api/v1/translations/{code}/{lang}/review    → Mark as reviewed
DELETE /api/v1/translations/{code}/{lang}           → Delete (non-EN)
POST   /api/v1/translations/bulk                    → Bulk import (up to 5,000)
```

### Languages

```
GET   /api/v1/languages                 → List active languages
GET   /api/v1/languages/{code}          → Get language
POST  /api/v1/languages                 → Create language
PUT   /api/v1/languages/{code}          → Update name/nativeName/cultureTag
PATCH /api/v1/languages/{code}/active   → Activate/deactivate
PATCH /api/v1/languages/{code}/default  → Set as default language
```

### Locales

```
GET /api/v1/locales         → All configurations
GET /api/v1/locales/{lang}  → Configuration for a language
PUT /api/v1/locales/{lang}  → Create or update (upsert)
```

### Currencies

```
GET    /api/v1/currencies/{lang}             → All formats for a language
PUT    /api/v1/currencies/{lang}/{currency}  → Create or update format
DELETE /api/v1/currencies/{lang}/{currency}  → Delete format
```

## Authentication

The service uses JWT Bearer, which is shared across the ATLAS platform.
Authorization policies are:

| Policy | Allowed Roles                           | Endpoints |
|---|-----------------------------------------|---|
| `i18n.read` | Any authenticated user                  | GET (public read access within ATLAS) |
| `i18n.write` | `KUKULCAN.Admin`, `KUKULCAN.i18n.Admin` | POST / PUT / PATCH / DELETE |

## How to Add a New Language

1. **POST** `/api/v1/languages` with the ISO 639-1 code, name, and `cultureTag`.
2. **PUT** `/api/v1/locales/{code}` to configure date/number formats.
3. **PUT** `/api/v1/currencies/{code}/EUR` (and any other relevant currencies).
4. Use **POST** `/api/v1/translations/bulk` to upload all translations for the new language.

---

## How to Add a New ATLAS Module

1. Reserve the module prefix (2–5 letters) in the ATLAS catalog. Examples:  `CRM`, `PIM`, `WMS`, `ERP`, `SCM`.
2. The module can start creating translations immediately with **POST** `/api/v1/translations` or vía **bulk**.
3. It is recommended to start codes at `0001` and reserve ranges by subsystem (e.g. `CRM0001–CRM0099` for entities, `CRM0100–CRM0199` for errors, `CRM0200–CRM0299` for UI labels).

## Configuración de caché

| Nivel | Backend | Default TTL | Scope |
|---|---|---|---|
| L1 | `IMemoryCache` (in-process) | 5 minutes | Per instance |
| L2 | Redis | 1 hour (translations) / 6 hours (locales/currencies) | Shared across replicas |

To force reload the cache for an entire module, the bulk update endpoint can be used or you can wait for natural expiration. 
No manual flush endpoint is exposed (it can be implemented in CacheKeys.TranslationPrefix).
